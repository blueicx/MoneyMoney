# MoneyMoney 网页性能与请求治理设计

## 范围校正与现状证据

工作区按需加载已经实现并有自动化覆盖。本轮保留它，不重复拆模块。基线来自仓库 `scripts/web-loading-benchmark.cjs`：隔离本地服务、真实 Provider、Chromium、80ms RTT、750kbps、4×CPU 限速，AAPL 5 分钟图表，桌面与手机分别三次冷/热配对。

| 视口 | 冷工作区中位数 | 冷图表稳定中位数 | 热工作区中位数 | 热图表稳定中位数 |
|---|---:|---:|---:|---:|
| 桌面 1440px | 2746ms | 4598ms | 407ms | 1718ms |
| 手机 390px | 2498ms | 4583ms | 454ms | 1758ms |

冷加载 JavaScript 传输中位数约 151KB，热加载命中浏览器缓存后为 0。基线还显示，核心 dashboard runtime 之后的兼容脚本由动态 `async` 脚本逐个 `await` 下载；脚本依赖顺序需要保留，但网络下载可以并发。首页 `/api/stock/indices` 与 `/api/workspace/dashboard` 的股票指数 Provider 共用已完成缓存，却各自直接调用 Tencent；冷缓存并发时可能重复上游请求。现有 `getFreshExternal` 已提供同键缓存和单飞能力。

## 目标

1. 让核心 runtime 完成初始化后，兼容脚本并发下载、仍按原插入顺序执行，维持原有错误提示、事件和全局初始化语义。
2. 让股票指数接口和驾驶舱 Provider 共用同一数据加载函数及现有 60 秒单飞缓存，保留各自 API 响应格式、来源说明和错误语义。
3. 用同一真实数据 Chromium 基准报告冷/热工作区、图表稳定时间、脚本资源瀑布和 API 耗时。要求脚本瀑布消失、K线稳定时间不回退；外部 Provider 波动单独披露，不承诺不现实的固定百分比。

## 保持不变

- 市场工作区仍按需加载；研究、图表、比较和合约包不进入不相关首屏。
- 不改 DOM 布局、主题、市场隔离、K 线数据语义或任何交易配置。
- 私人 API 缓存边界不变；仅公开的股票指数摘要使用已有短缓存。
- 不改数据库、数据湖、AI 跑单、Telegram、服务端路由结构或依赖。

## 实施

### 启动兼容脚本

保留首个 dashboard runtime 单独下载，并继续等待认证和 `window.mm_dashboardReady`。对余下兼容脚本创建动态经典脚本，设置 `async=false` 并按清单顺序插入；浏览器可并发取回资源，但按插入顺序执行。等待该批次全部完成后，才派发 `mm-dashboard-runtime-loaded`。任何资源失败仍进入当前网络状态错误提示。

### 股票指数单飞

新增单一 `loadStockIndicesData()` 加载入口，内部通过 `getFreshExternal('stockIndices', CACHE_TTL, loader)` 获取/刷新并规范化数据。`dashboardStockIndices()` 和 `/api/stock/indices` 都调用它。成功的空数组在现有短 TTL 内也作为来源成功的空结果复用；Provider 异常仍不缓存，由既有 API/Provider 错误路径报告。

## 测试策略

- 构建产物测试验证 bootstrap 等待核心 runtime、兼容脚本使用有序动态执行、同一批次启动所有下载，并在全部完成后发事件。
- 源码接线测试验证两个指数调用者共用唯一 `loadStockIndicesData()`，腾讯指数 URL 只在共享 loader 中出现一次，loader 使用现有单飞缓存键。
- 现有 Chromium 基准在实现前后各运行桌面/手机三组冷/热配对，检查工作区及 K 线真实终态、脚本缓存、API 单次请求与兼容脚本资源起始时间跨度。
- 全量单测、构建、Web/认证/浏览器冒烟、安全扫描和差异检查后，才按既有流程推送、备份并部署；保留数据库与数据湖，只操作 `moneymoney.service`。

## 风险

- 兼容脚本间存在顺序依赖：用 `async=false` 保序，并在桌面/手机真实页面验证初始化事件与图表稳定状态。
- 慢外部 K 线 Provider 会限制整体体验改善：分开报告浏览器脚本、HTTP API 与最终图表时间，不把上游波动归功于或归咎于脚本优化。
- 首页股票指数为空时短暂缓存空数组：只限于现有 60 秒短缓存，不影响 K 线、不跨市场回退；异常 rejection 不进入缓存。

## 实测结果

相同基准参数实现前/后各三次，冷/热配对，桌面与手机分开。实现后冷兼容脚本 4 个资源请求起始跨度中位数为桌面 2.9ms、手机 3.0ms；热缓存对应约 1.2ms、3.7ms，四个资源总传输约 26.5KB，热缓存为 0。脚本执行依赖顺序保持，浏览器矩阵与实时 K 线冒烟通过。

| 视口 | 阶段 | 冷工作区 | 冷 K线稳定 | 热工作区 | 热 K线稳定 |
|---|---|---:|---:|---:|---:|
| 桌面 | 实现前 | 2746ms | 4598ms | 407ms | 1718ms |
| 桌面 | 实现后 | 3019ms | 4992ms | 494ms | 1837ms |
| 手机 | 实现前 | 2498ms | 4583ms | 454ms | 1758ms |
| 手机 | 实现后 | 2686ms | 4790ms | 478ms | 1802ms |

三次小样本的端到端中位数没有显示整体提速；实现后的样本出现较慢 K 线请求，反映外部 Provider 波动。故本轮只确认消除了兼容脚本下载瀑布及合并了同一指数来源的并发请求，不宣称总加载速度已改善。当前应继续优化/观测的主要瓶颈是 `/api/stock/kline` 的上游等待，而非静态脚本缓存；任何进一步优化都需保留来源状态和时点正确性，不能伪造或跨范围复用行情。
