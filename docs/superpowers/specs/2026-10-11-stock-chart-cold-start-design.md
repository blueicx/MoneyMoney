# 股票 K 线首屏冷启动优化设计

日期：2026-10-11
范围：MoneyMoney 股票行情工作区的首屏 K 线加载关键路径。此为持续“全做”路线的第一批，不重复实现已交付能力。

## 背景与基线

当前线上运行代码位于 `codex/research-closure-all`，提交 `b6629d9`；根工作树 `master` 的 `4d44480` 是较旧运行代码上的交接文档提交，不能作为本批基线。未跟踪数据库与其他用户文件均不纳入本设计或提交。

使用隔离数据目录、本地 MoneyMoney 服务、真实公开 Provider、Chromium 4× CPU 降速、80ms RTT 和 750kbps 下载，执行 3 组桌面/手机冷、热配对：

| 视口 | 冷启动工作区 | 冷启动图表可用 | 热启动工作区 | 热启动图表可用 |
|---|---:|---:|---:|---:|
| 桌面 1440px | 3944ms | 4879ms | 921ms | 1175ms |
| 手机 390px | 3681ms | 4738ms | 902ms | 1195ms |

共 12 次导航中，API 端到端耗时中位数（冷、热与两种视口混合）为：K 线 194ms、股票指数 206ms、工作区导航 654ms、自选 632ms、模拟持仓 632ms。混合中位数不代表单独的冷请求或服务端耗时；当前证据不足以把冷启动归因于 Yahoo Provider。图表加载也必须新增分阶段测量，不能把脚本下载、网络等待和首次绘制混为一个指标。

## 目标

- 尽早显示当前股票与周期的有效 K 线，降低首屏到图表可操作的时间。
- K 线不得等待指数、自选、模拟持仓或非当前工作区内容；这些区域仍在首屏独立加载，并保留真实加载/空/失败状态。
- 保留四市场与工作区隔离、上下文取消、请求去重、数据状态、来源时间和历史行为。
- 通过分阶段指标找出实际关键路径；如果下载/模块解析而非请求顺序占主导，再按证据决定是否拆分图表资源。

## 方案比较

1. **优先解耦关键路径（推荐）**：图表资源和当前 K 线请求优先启动；指数、自选、持仓及导航数据独立加载。对首屏链路添加阶段计时。改动集中、风险较低，直接针对已测得的冷/热差异。
2. **拆分图表资源**：将图表核心从工作区脚本中分离并提前下载。潜在收益较高，但模块依赖和构建/缓存边界更复杂；仅当阶段计时证明图表资源下载或解析是主要瓶颈时采用。
3. **扩大缓存或允许旧数据先显示**：可能缩短等待，但容易混淆过期与最新行情，增加错误决策风险。本批不采用，也不以陈旧数据冒充新鲜数据。

本设计选择方案 1，并把方案 2 设为由测量结果触发的同一批内可选优化；不实施方案 3。

## 设计与数据流

### 首屏关键路径

- 仅在管理员或访客可访问的股票行情工作区、标的身份和周期已经确定后启动当前 K 线加载。
- 图表核心资源与核心工作区启动并发下载；若资源必须等核心 runtime 后才能执行，则可提前下载但不得提前执行依赖未就绪的脚本。
- 当前 K 线 API 与图表首次绘制不等待指数卡片、自选列表、模拟持仓或其他工作区模块。右侧标的库继续显示独立占位、加载和失败状态，内容到达后原位更新。
- 非股票工作区不预加载股票图表资源，不调用股票 K 线接口。市场、标的、周期切换继续使用当前上下文版本和 AbortSignal，旧响应不得覆盖新页面。
- 首屏当前 K 线请求保持单次、可取消和现有图表窗口限制；分页、asOf、指定日内、回测和策略历史范围不改变。

### 阶段计时

在开发/基准测试中采集而非公开暴露私人数据：导航提交、认证就绪、核心 runtime 就绪、图表资源请求/加载、K 线 API 请求/响应、Canvas 首次绘制和首个可交互图表。基准同时记录每个 API 的请求起止、状态码、资源传输字节、数据状态、来源与图表根数。真实来源基准与可控延迟测试分开报告。

阶段标记只用于观测，不向访客响应或服务端日志写入自选、持仓等私人内容。K 线 API 的业务响应形状、no-store 及缓存状态语义保持兼容。

### 状态和失败处理

- 正常数据：按现有来源状态渲染并显示来源及时间。
- K 线等待期间：显示现有图表加载状态；指数、自选或持仓较慢不遮盖图表。
- K 线为空、失败或超时：保留当前明确原因、重试和历史/时点边界，不回退到过期行情、不跨市场取数。
- 辅助接口失败：仅对应辅助区域显示失败；不能清空已加载 K 线。
- 用户切换标的/市场/功能：中止旧请求并忽略迟到响应；隐藏的工作区不持续轮询或绘图。

## 验收

1. 先新增可失败的隔离 Chromium 测试：人为延迟指数、自选或模拟持仓接口时，图表仍在其前完成；每次导航 K 线请求恰好一次；迟到旧上下文响应不会覆盖新标的。
2. 对四市场和对应工作区检查资源/API隔离；访客私有数据权限不变。手机和三个主题均显示辅助区域独立状态。
3. 覆盖 K 线成功、空结果、来源失败、超时、缓存/历史状态以及用户切换中止；不改变 `asOf`、日内下钻、分页、Replay、回测和交易模拟行为。
4. 同环境 4×CPU、80ms RTT、750kbps，桌面 1440px 与手机 390px 各至少 3 组冷/热配对；图表 API 和来源状态也记录。目标是冷启动图表可用中位数较本设计基线改善至少 20%，热启动不回归；若真实 Provider 波动掩盖目标，另用固定响应/可控延迟证明关键路径解耦，并如实报告真实来源结果，不以模拟数据宣称线上提速。
5. 通过完整自动测试、构建、Web/认证/浏览器/实时 K 线冒烟、安全扫描和 `git diff --check`。生产发布另行备份、校验 Hash、检查正式域名/健康/版本并保留回滚；只操作 `moneymoney.service`，不触碰数据库、数据湖或其他服务。

## 明确不做

- 不允许用 stale-while-revalidate 旧行情填补冷启动。
- 不改股票源、刷新频率、市场数据授权口径或 K 线 API 范围。
- 不为追求性能降低权限校验，不缓存私人响应，不改变 AI 跑单、预算、模型路由、订单或实盘执行边界。
- 不在本批重写前端框架或进行无关模块拆分；其他功能扩展按后续批次继续，不以当前性能批替代全量路线。
